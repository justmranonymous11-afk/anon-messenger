Generate a unique code in your browser and share it via any channel — Signal, email, in person. Nothing is sent to any server yet.

Keys exchange in your browser

Questions

How do I connect without an account?
Generate a room code and share it with the other person. Both of you enter the same code and you're connected. That's it — no email, no password, no profile.
What happens when I close the tab?
The session ends immediately and everything is gone. Messages exist only in your browser's RAM during the session — they are never written to disk, a database, or any log file. There is no history.
Can the server administrator read my messages?
No. Encryption keys are negotiated directly between your browsers via ECDH. The server only relays encrypted blobs; it has no keys and cannot read any content. Even a full server compromise reveals nothing about message contents.
What doesn't ANON protect against?
ANON is strong against server-side threats — but it does not protect against: screenshots by the other person, malware already running on your device, or someone physically looking at your screen. The full breakdown is in the Security model.
Does publishing the source code break the encryption?
No — and this is a crucial point. This is Kerckhoffs's principle: a secure system should remain secure even if everything about it except the key is public knowledge. ANON's protection comes from your ephemeral session keys (generated fresh each time, never stored), not from keeping the algorithm secret. Publishing the source code lets anyone verify there are no backdoors — which actually strengthens trust. The server seeing the code cannot derive your keys.

Security model

ANON uses standard cryptographic primitives built into your browser's Web Crypto API — the same engine used by banking apps and TLS. No custom crypto, no proprietary algorithms, no third-party dependencies for encryption.

1
Key exchange — ECDH P-256

Each browser generates a fresh keypair on connect. Public keys are exchanged through the signaling server. The resulting shared secret never leaves your device and the server never sees it.

↓
2
Key derivation — HKDF / SHA-256

The shared secret is stretched into a 256-bit AES session key via HKDF. The key is marked non-extractable — it physically cannot be read out of the browser by any JavaScript, including this page.

↓
3
Encryption — AES-GCM 256, random IV per message

Every message is encrypted with a fresh 96-bit random IV before it leaves your device. The WebRTC transport also applies its own DTLS layer — messages are double-encrypted in transit. The server relays ciphertext it cannot read.

Protected
  • Server reading your messages
  • Database breaches (no data stored)
  • Network interception
  • Replay attacks (random IV per msg)
  • Server-side metadata logging
Outside the threat model
  • Screenshots by the other person
  • Malware already on your device
  • Physical shoulder-surfing
  • Legal seizure of your own device
Opening the source code does not break privacy. This is Kerckhoffs's principle — a secure system must remain secure even if everything about it except the key is public. Your session keys are generated fresh each time using the browser's CSPRNG and are never stored anywhere. An adversary who reads every line of this code still cannot derive your keys. Publishing the source code lets anyone audit for backdoors — which makes ANON more trustworthy, not less.
